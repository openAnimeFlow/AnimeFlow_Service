# 本地收藏与 Bangumi 双向同步重构计划

日期：2026-09-19。本文为实施计划，本次不修改业务代码、不执行数据库迁移、不写入 Bangumi。当.md文件提交git

## 1. 目标与约定

1. 用户登录 AnimeFlow 后即可新增、更新本地收藏，不强制绑定 Bangumi。
2. 未绑定时仅更新 `anime_flow.user_bgm_collection`；已绑定时保存本地修改并立即尝试更新 Bangumi。远端失败时保留本地结果，明确告知同步状态，支持恢复。
3. `POST /api/v1/users/collections/sync` 从单向导入改为双向合并：保留 Bangumi → 本地能力，增加本地 → Bangumi。
4. 同一用户、同一条目两侧收藏分类不一致时，不自动决定覆盖方向，由客户端账号设置页`lib/features/settings/presentation/pages/account_settings_page.dart`展示冲突并让用户选择最终分类。最终分类同时应用到两侧。
5. 本文“本地”指 AnimeFlow 服务端数据库，不表示 Flutter 离线存储。本轮不实现离线收藏、取消收藏的双向删除传播。
6. 分类为 `1=想看、2=看过、3=在看、4=搁置、5=抛弃`，与条目大类 `subjectType` 分开处理。

以下失败策略、字段合并规则和新接口是建议采用的设计，不是当前已有能力。

## 2. 已核验的现状

### 2.1 MySQL MCP 实库检查

已通过 MySQL MCP 执行 `SELECT DATABASE()`、表结构读取、`SHOW CREATE TABLE`、表清单和聚合查询，当前数据库为 `anime_flow`。此前默认库 `dianshang` 的连接问题已解除。未读取 OAuth token 内容。

| 实库事实 | 重构影响 |
| --- | --- |
| 收藏共 183 条，属于 1 个用户，全部为动画 `subject_type=2` | 现有数据不能覆盖其他条目大类，需补充测试数据 |
| 分类 1/2/3/4/5 数量分别为 33/101/11/31/7 | 可作为迁移前后数量核对基线，实施时应重新统计 |
| `bgm_interest_id BIGINT NOT NULL`，具有全局唯一索引 | 无 Bangumi 收藏 ID 的本地收藏无法正常新增 |
| 唯一键 `uk_user_subject(user_id, subject_id)` | 应继续作为本地收藏业务身份 |
| `bgm_updated_at BIGINT NOT NULL` | 不能用伪造的远端更新时间表示本地编辑时间 |
| `sync_time` 带 `ON UPDATE CURRENT_TIMESTAMP` | 当前字段不能准确表示“最后成功同步时间” |
| 同时存在 `is_private` 和 `private`，有 3 行值不一致 | 列表与详情可能展示不同隐私状态，迁移需统一 |
| 当前没有同步任务表、同步明细表和冲突表 | 用户离开页面后的恢复需要持久化能力 |

### 2.2 服务端实际行为

- `CollectionController.updateCollection` 使用 Flow token 鉴权，调用 `UserBgmCollectionServiceImpl.updateCollection`；真正的绑定要求在下游 OAuth 执行链。
- 当前更新顺序是：调用 Bangumi 更新 → 获取 Bangumi 条目详情 → 写入本地。无绑定无法走通；远端成功而本地失败时也缺少恢复记录。
- 本地新增要求 `bgmInterestId` 非空，`subjectType` 被硬编码为 2；DTO 虽含 `subjectType`，实际未使用。
- `UpdateUserCollectionDto.hasUpdateField()` 不把空标签列表作为有效更新，无法单独清空标签；`progress` 只转发上游，没有完整的本地等价处理。
- `UserBgmCollectionSyncRunner` 按五种分类分页拉取，直接覆盖已有收藏，最后删除 `sync_time < syncStartTime` 的用户收藏。删除条件未限制 `subject_type`，会危及本地独有收藏及其他大类收藏。
- 同步总量按各页 `total` 的最大值计算，不能代表五类合并后的任务总量。
- 任务状态仅保存在 Redis，TTL 24 小时；锁 TTL 30 分钟，锁值固定为 `1`，没有持有者校验及续租。
- `UserBgmCollectionMapper.xml` 列表读 `is_private`，详情读旧 `private`，排序依赖 `bgm_updated_at`。
- 解绑当前只删除 OAuth 记录，不删除收藏；应保留这一行为，并补充任务失效处理。

## 3. 业务规则

### 3.1 单条更新

| 场景 | 本地结果 | Bangumi 行为 / 返回状态 |
| --- | --- | --- |
| 未登录 | 不写入 | 返回现有登录错误 |
| 已登录、未绑定 | 保存 | 不调用 Bangumi，`LOCAL_ONLY` |
| 已绑定且调用成功 | 保存 | 同步后 `SYNCED` |
| 已绑定、授权不可恢复 | 保留修改 | `AUTH_REQUIRED`，提示重新授权 |
| 已绑定、超时/限流/暂时故障 | 保留修改 | `PENDING`，持久化待重试记录 |
| 请求或本地事务失败 | 不产生本次远端写入 | 返回校验/保存错误 |

采用“本地事务先提交，事务外立即尝试远端写入”的方式，避免网络调用占用数据库事务。成功响应必须携带 `localSaved`、`remoteSyncStatus`；不能把部分成功显示为两侧同步成功。

新增收藏必须传 `type`；已有收藏按字段存在性进行部分更新，未传字段不覆盖。空字符串、空标签列表和评分 0 应支持清空。条目大类优先由本地条目元数据确认，与传入值校验一致；只接受 1、2、3、4、6，不接受 5，不再统一写 2。

`progress` 是布尔操作，不等同于已看话数。实施前核验当前 Bangumi 客户端对应接口的真实语义，并定义与 `user_episode_watch`、`ep_status` 的一致处理。没有本地等价实现时应明确拒绝不支持的操作，不能返回成功却丢弃字段；该项是完整上线的验收门槛。

### 3.2 批量同步合并矩阵

以 `(user_id, subject_id)` 配对，并限制当前任务的 `subjectType`。

| 本地 | Bangumi | 行为 |
| --- | --- | --- |
| 有 | 无 | 上传本地收藏，不删除本地 |
| 无 | 有 | 导入本地 |
| 有，分类 A | 有，分类 A | 无分类冲突，按字段合并策略处理 |
| 有，分类 A | 有，分类 B | 保存冲突快照，暂停该条目写入，用户决定最终分类 |

远端“没有”必须建立在完整拉取成功或明确的单条不存在响应上，不能把超时、401、403、分页失败、解析失败当作空收藏。

保留双方数据的并集，不推断删除。远端单独取消收藏后再次同步可能被本地重新上传，这是本轮明确的合并语义。若未来需要删除传播，应单独设计删除标记和共同同步基线。

### 3.3 非分类字段合并范围

- 分类冲突弹窗只决定 `type`，不能顺带覆盖评论、标签、评分、隐私和观看进度。
- 仅一侧存在时复制该侧支持的字段；上传不得把未编辑的默认值无条件覆盖到已有远端收藏。
- 双侧存在且分类一致时：本地明确编辑过的字段优先上传，其余支持字段沿用远端导入；用 `dirty_fields` 记录本地编辑意图，禁止仅靠时间戳猜测。
- 此规则意味着非分类字段双方都改过时，本地脏字段优先。本轮不扩展为全字段人工冲突 UI，需在同步说明中写明。
- 远端不支持精确写入的进度字段保留本地，并标明同步范围，不能用 `progress=true` 替代任意话数。
- 类型冲突未解决时，冻结该条目整个批量同步明细及对应自动重试，防止旁路任务提前覆盖分类。

## 4. 数据库改造

保留 `user_bgm_collection` 表名，避免同时扩大命名迁移范围。新增迁移文件建议为 `db/migrations/20260919_collection_bidirectional_sync.sql`；以下为结构设计，最终 DDL 需结合迁移演练确定。

### 4.1 收藏表

| 字段 / 索引 | 建议调整 |
| --- | --- |
| `bgm_interest_id` | 允许 NULL，无远端记录时保持 NULL，不使用 0 或本地主键伪装 |
| `bgm_updated_at` | 允许 NULL，仅保存远端时间 |
| `sync_time` | 允许 NULL，取消自动更新时间，只在两侧成功对齐后显式写入 |
| `local_updated_at DATETIME(3)` | 本地内容最后修改时间，由业务层维护 |
| `version BIGINT NOT NULL DEFAULT 0` | 乐观锁版本，修改内容时递增 |
| `dirty_fields JSON` | 待上传字段集合，保存明确的本地修改意图 |
| `remote_sync_status VARCHAR(32)` | `LOCAL_ONLY/PENDING/SYNCED/AUTH_REQUIRED/CONFLICT` |
| `bgm_account_uid BIGINT NULL` | 标识远端记录归属，避免换绑后沿用旧账号的关联 |
| `uk_user_subject` | 保留，配合原子 upsert 或版本条件更新 |
| `uk_bgm_interest_id` | 评估改为普通查询索引；跨本地用户的业务唯一性由本地键保证，远端归属另行校验 |
| 列表排序索引 | 增加匹配 `user_id/type/subject_type/local_updated_at/id` 的索引，排序添加 `id` 稳定分页 |

历史行保留原值，初始化 `local_updated_at` 可用原 `sync_time/create_time`，不宣称其等于真实用户编辑时间。历史绑定归属无法确定的行保持待核验；首次新同步再建立关联，不把所有历史行盲目标记为已同步。

隐私字段统一使用 `is_private`，先修正详情 Mapper；迁移前备份 3 条差异记录，以当前写入路径使用的 `is_private` 为主，保留审计。旧 `private` 列先保留，待所有读写切换验证后再删除。

### 4.2 持久化任务与明细

新增两张表即可覆盖执行与冲突，不必把冲突只存 Redis：

1. `user_bgm_collection_sync_task`：`id`、`user_id`、`subject_type`、`bgm_account_uid`、绑定代次、`status`、`phase`、各类计数、错误码、创建/开始/完成时间、`version`、执行租约/心跳。数据库约束或用户级活动任务登记保证一个用户仅有一个活动全量任务。
2. `user_bgm_collection_sync_item`：`id`、`task_id`（单条待上传记录可为空）、`user_id`、`subject_id`、目标账号及绑定代次、操作来源、操作类型、状态、`local_version`、本地/远端快照、远端指纹、`selected_type`、冲突版本、重试次数、下次重试时间、错误码、幂等键、时间字段。

任务明细唯一键建议 `(task_id, subject_id)`；单条上传记录另设唯一幂等键，例如“用户 + 条目 + 本地版本 + 绑定代次”。索引覆盖任务分页、用户待解决冲突、待重试时间。Redis 仅缓存进度和辅助锁，数据库为事实来源。

快照只保留收藏字段，不存 access token、refresh token；冲突查询必须校验用户归属。任务明细需设定保留期，但未解决冲突不能因 Redis 过期而丢失。

## 5. 服务端执行流程

### 5.1 单条保存与可靠上传

1. Flow 鉴权、校验参数、读取本地收藏及当前绑定。
2. 在本地短事务内保存收藏、递增版本、记录脏字段；已绑定时同时写入上传明细，保证重启后仍可恢复。
3. 未绑定直接返回 `LOCAL_ONLY`；已绑定通过现有 `BangumiOAuthExecutor` 立即尝试上传，复用刷新 token 能力。
4. 按用户与条目串行执行远端写入；每次发出请求前检查绑定代次、本地版本及未解决冲突。
5. 远端写入成功后读取确认结果，按预期本地版本回写远端元数据，只清理已成功发送且版本未改变的脏字段。
6. 超时等不确定结果先读远端核对，再决定重试；禁止旧版本重试覆盖新版本。绑定失效与普通网络故障分开记录。
7. 已存在冲突时，新的本地编辑可以保存，但不直接绕过冲突上传；使旧决议失效，刷新冲突版本并提示继续处理。

普通单条编辑是用户明确的更新意图；全量同步发现的差异必须遵循人工冲突规则。尚未发现冲突的历史待上传记录在绑定变化或全量扫描后也必须重新比较，不能盲目重放。

### 5.2 全量同步

1. 提交时仍要求绑定；未绑定允许普通收藏，但无法提交 Bangumi 同步。
2. 若有活动任务或待解决冲突，返回原任务，避免覆盖；10 分钟冷却只限制新全量扫描，不限制冲突提交与失败明细重试。
3. 固定目标账号及绑定代次，先提交持久化任务，再通过异步执行器唤醒执行；增加数据库任务扫描与租约恢复机制，不能只依赖内存中的 `@Async` 调用。
4. `SCANNING`：按五分类完整拉取到暂存明细，按条目 ID 去重，分页异常停止；此阶段不直接覆盖正式收藏。
5. 扫描完成后，对本地与远端快照执行合并矩阵，生成导入、上传、无变化及冲突明细。
6. `APPLYING`：先执行无冲突项。写入前重新校验本地版本；上传前重新读取目标远端收藏确认关键字段，变化则重新规划或生成冲突。
7. 无冲突项处理完但仍有冲突，进入 `WAITING_CONFLICT`；释放工作租约，保留数据库活动任务和冲突。用户可以退出页面后继续处理。
8. 收到决议后恢复执行对应明细，全部完成才标记成功。失败项保留重试，不重复执行已完成项。
9. 删除旧的 `sync_time` 批量删除代码。任务中所有读写均限制用户、条目大类和账号身份。

任务状态建议：`QUEUED/RUNNING/WAITING_CONFLICT/PARTIAL_FAILED/SUCCESS/FAILED/CANCELLED`；无任务时查询返回 `IDLE`。运行阶段用 `phase=SCANNING/APPLYING/RESOLVING` 表示，客户端不通过消息文本推断状态。

扫描期间总量未知时返回空总量并展示不定进度；扫描完成后以去重条目并集为总量。分别提供 `uploadedCount/importedCount/unchangedCount/conflictCount/resolvedCount/failedCount`，保留旧计数字段时明确其含义。

### 5.3 冲突提交与并发

- 服务端记录 `localType`、`remoteType`、`localVersion`、`remoteFingerprint`、`conflictVersion`。
- 客户端提交条目冲突 ID、所见冲突版本及 `selectedType`；服务端只接受 1～5。
- 提交时检查归属、任务状态、当前绑定和本地版本，并重新读取远端。任一侧变化则更新冲突快照，返回 `STALE_CONFLICT`，让用户重新确认。
- 选择本地类型：上传该类型；选择远端类型：更新本地；选择第三种类型：两侧更新为新值。远端已等于目标值时不重复写入。
- 决议先持久化为待执行操作，不能立即标记已解决；远端确认及本地版本条件提交成功后才算完成。
- 批量提交支持逐项结果，失败项可重试；同一幂等键重复提交同样决议返回原结果，不重复执行。相反决议不能复用同一幂等键。
- 单条编辑、全量同步、冲突恢复、重试共用每用户每条目的写入串行机制。Redis 锁使用随机持有者值、续租和原子比较释放，不能旧任务直接删除新任务的锁。
- Bangumi 若不提供条件更新，读前校验无法彻底消除“读取后、写入前”的外部编辑竞争；应写后核验、保留操作快照并重新报冲突，不承诺跨系统强事务。
- 解绑或换绑递增绑定代次并取消旧任务；旧明细不得恢复到新账号。已发出的外部请求不能撤回，其结果只用于旧任务审计，不能回填为新账号同步成功。

### 5.4 提交后离开页面、关闭应用与恢复

核心原则：服务端任务生命周期独立于页面、客户端进程和 HTTP 连接；冲突是持久化待办，不是必须当场响应的弹窗。

| 离开时机 | 服务端处理 | 再次进入应用后的行为 |
| --- | --- | --- |
| 请求尚未到达服务端 | 不存在任务，不假定已提交 | 查询状态；必要时使用原幂等键重试提交 |
| 任务已入库，但响应丢失/应用关闭 | 继续执行已接收任务 | 查询活动任务恢复，不因未拿到 `taskId` 重复创建 |
| 正在扫描或执行无冲突项 | 后台继续，不受客户端取消请求或停止轮询影响 | 展示最新进度，恢复必要轮询 |
| 扫描发现分类冲突 | 保存冲突，继续处理其他无冲突项；之后等待人工处理 | 显示待处理数量与入口，由用户决定何时处理 |
| 用户已选分类但尚未提交 | 不修改服务端决议与双方收藏 | 可恢复客户端草稿，但必须重新校验版本；草稿不等于授权提交 |
| 决议已入库，但响应丢失/应用关闭 | 按已提交决议继续执行，失败保留可重试状态 | 查询决议/明细结果，以原幂等键重试不会重复执行 |
| 长时间不再打开应用 | 未解决项保持暂停，不超时自动采用任一侧分类 | 下次登录仍可发现待办；处理前刷新双侧快照 |

**接收与执行保障：**

- 创建任务和提交冲突决议均在数据库事务成功后才返回“已接收”。先持久化，再触发执行，不能先响应后仅放入内存队列。
- 创建任务也接受客户端生成的 `requestId`，以用户与幂等键建立唯一约束；客户端在发送前保存该键，响应不确定时复用。不同设备使用不同键时，仍由每用户一个活动全量任务的约束去重。
- 定时调度器领取已提交的排队任务、到期重试项及租约超时的运行任务。进程在“入库后、调度前”崩溃也能恢复。通过事务领取/条件更新防止多实例重复执行。
- 服务端不依赖客户端心跳保活。客户端退出页面、切后台、退出登录或关闭进程仅停止客户端请求，不自动取消任务；解绑/换绑的取消规则仍按 5.3 执行。
- `WAITING_CONFLICT` 不占工作线程、不循环等待用户、不持有长期执行锁，也不消耗自动重试次数；只保留业务层活动任务登记。其他条目的普通收藏修改继续可用。
- 同时存在失败项和未解决冲突时，使用 `WAITING_CONFLICT` 并保留 `failedCount`，客户端同时展示两类待办；冲突清零但仍有失败项时转 `PARTIAL_FAILED`，全部成功才转 `SUCCESS`。
- 不设置“超时默认选本地/远端”。未解决冲突不得被常规历史任务清理删除；未来若引入过期归档，应仍保留待办并要求重新扫描后确认，不能自动覆盖数据。

**重新发现待办：**

- `GET /sync` 优先返回当前用户活动/待处理任务，无活动任务时才返回最近终态任务；返回 `pendingConflictCount`、`failedCount`、`statusVersion` 和目标账号标识。客户端无需记住原来的 `taskId` 才能恢复。
- 登录完成、应用冷启动恢复登录态、应用回到前台、进入账号设置页时进行一次状态查询；合并重复请求，离线失败保留上次展示但标记未刷新，不把未知状态当作无冲突。
- 待办提示由登录后的应用级状态协调，不只由账号设置页挂载触发。个人中心/设置入口显示“收藏同步有 N 项待处理”，账号设置页提供持久入口。
- 不因发现冲突强制跳转或反复弹窗。按用户、任务及状态版本去重短提示；忽略提示不消除待办。跨设备重新登录也以服务端结果为准。
- 应用关闭期间无需客户端后台常驻。本轮以再次打开后的站内提示保证可发现；系统推送不是完成同步的前提，如后续增加推送，只用于提醒，点击后仍查询服务端状态。

**冲突选择草稿：**

- 可在客户端保存未提交选择，键包含用户、绑定代次、任务 ID、冲突 ID 与冲突版本；重新打开后先获取最新冲突再恢复有效草稿。
- 版本变化、另一设备已解决、任务取消或绑定变化时使对应草稿失效；退出登录清理该用户草稿。未做草稿持久化时，允许重新选择，但服务端冲突本身必须仍在。
- 点击提交后不能仅靠关闭弹窗表示完成。页面可立即离开，结果由服务端持久化状态决定；再次打开能区分“未提交”“已接收待执行”“已解决”“失败待重试”。

## 6. API 契约建议

保留 `/api/v1/users/collections` 根路径，沿用现有 `Result` 包装。以下为建议新增/扩展契约。

| 接口 | 用途 |
| --- | --- |
| `PUT /{subjectId}` | 本地保存并按绑定情况上传，返回 `localSaved/remoteSyncStatus/localVersion` |
| `POST /sync?subjectType=2` | 请求体携带 `requestId`，幂等创建或返回已有双向同步任务 |
| `GET /sync` | 优先返回当前用户活动/待处理任务，否则最近任务，含 `taskId/status/phase/statusVersion` 及待办计数 |
| `GET /sync/{taskId}` | 查询指定任务及决议执行摘要，用于响应丢失、跨页面恢复；校验用户归属 |
| `GET /sync/{taskId}/conflicts?offset=0&limit=20` | 分页读取冲突，包含名称、封面、双侧分类和版本 |
| `POST /sync/{taskId}/conflicts/resolve` | 持久化用户决议并恢复异步执行 |
| `POST /sync/{taskId}/retry` | 仅重试可恢复失败项 |

冲突提交数据示例：

```json
{
  "requestId": "client-generated-unique-id",
  "items": [
    {"conflictId": "123", "conflictVersion": 2, "selectedType": 3}
  ]
}
```

冲突 ID、任务 ID 可采用字符串传输，避免跨端整数精度问题。服务端从登录态取得 `userId`，不信任客户端提交用户身份。建议错误码包括 `BANGUMI_NOT_BOUND`、`BANGUMI_AUTH_REQUIRED`、`STALE_CONFLICT`、`SYNC_BINDING_CHANGED`；以现有全局异常和响应约定落地。

不要把存在收藏的依据继续绑定到 `interest.id`。列表/详情保留 `interest.type` 表示收藏，远端 ID 可空，可增补明确的本地收藏 ID。兼容旧客户端必须专项处理，不能只改数据库空值约束就上线。

## 7. Flutter 客户端改造

### 7.1 账号设置页交互

- 在 `account_settings_page.dart` 的 Bangumi 绑定区域继续复用同步组件，文案改为“双向同步收藏”。未绑定时说明可正常使用本地收藏，绑定用于同步。
- `BangumiCollectionSyncSection` 展示扫描、执行、待处理冲突、部分失败、完成状态。
- 有冲突时显示“有 N 条收藏分类不一致”和“处理冲突”入口，打开独立冲突页面/宽屏对话框，避免把全部逻辑塞进设置页。
- 每项显示条目名称、封面、本地分类、Bangumi 分类；可选“采用本地”“采用 Bangumi”或五种分类中的其他最终值。默认不预选，不自动覆盖。

### 7.2 数据层与缓存

- 扩展 `bgm_collection_sync_status_item.dart`；未知状态显示“未知状态/请刷新”，不再静默映射为未同步。
- 新增冲突数据模型和 Provider；扩展 `FlowApi` 及 `AnimeFlowApi` 路径常量。
- `bgm_collection_sync_provider.dart` 只在排队/执行阶段轮询；等待人工处理时停止高频轮询，进入页面或提交决议后刷新。
- `FlowApi.updateCollectionService` 返回保存结果；未绑定正常更新 UI，远端失败显示“本地已保存，Bangumi 待同步/需重新授权”。

- 同步导入或冲突解决后刷新收藏列表各分类、收藏数量和受影响详情；不只刷新 `currentUserInfoProvider`。
- 登录用户变化、退出登录和解绑时取消轮询、清空用户级缓存，防止旧异步响应污染新用户状态。

- 新增应用级同步待办协调 Provider，在登录恢复和应用生命周期回到前台时查询；页面销毁不触发服务端取消。用户离开账号设置页后，个人中心/设置入口仍能展示待办标记。
- 创建任务/提交决议的幂等键在发请求前保存；网络断开或超时显示“正在确认提交结果”，先查询服务端，再按原键重试，不直接报未提交或再次新建任务。

## 9. 测试与验收

1. 未绑定新增/编辑五类收藏成功；Bangumi 客户端零调用；列表、数量、详情一致，可空远端 ID 不导致 Flutter 解析异常。
2. 已绑定正常保存两侧一致；网络故障、授权失败分别返回可识别状态，本地数据保留；重启后待上传任务可恢复。
3. 新建缺少分类、非法分类/条目大类被拒绝；已有收藏部分更新不清空其他字段；清空标签、评论和评分正常。
4. 本地独有上传、远端独有导入、同类合并、异类冲突四种情况覆盖；原有本地记录与其他大类不被删除。
5. 五分类分页、多页、空页、重复条目、分页中断和远端动态变化均不误判为删除或缺失；总量统计与明细一致。
6. 冲突未选择时两侧分类不变；采用本地、采用远端、选择第三类均最终一致；退出页面/Redis 清空后能恢复待处理列表。
7. 冲突提交重复、部分失败、远端成功但回写失败、本地或远端提交前变化、恶意访问其他用户任务均有对应校验与恢复。
8. 同条目并发编辑、重复提交同步、多个工作实例、锁到期、进程重启、旧任务释放新锁均不导致旧版本覆盖新版本。
9. 解绑/换绑后本地收藏保留，旧任务不能写新账号；授权自动刷新不应误判为用户换绑。
10. 迁移前后收藏总数和分类数量核对、隐私差异修复、唯一约束和可空字段验证；旧客户端不能因新状态/空 ID 崩溃。
11. 提交同步后立即退出设置页、切后台、强制关闭应用：服务端继续无冲突工作；发生冲突时持久化等待，下次启动应用即可看到待办，不要求重新点击同步。
12. 创建任务/提交决议已入库但响应丢失：原幂等键重试返回原任务/结果；本地未收到 `taskId` 时也能通过 `GET /sync` 找回任务。
13. 服务端在任务入库后尚未启动工作线程时崩溃，以及执行中重启：调度器能重新领取；已完成明细不重复覆盖，未解决冲突不依赖 Redis 存活。
14. 超过 24 小时未处理、两个设备同时处理、草稿保存后收藏发生变化：待办不丢失，旧草稿/决议失效并要求重新选择；无超时自动覆盖。
15. 应用冷启动/回前台的查询去重、离线恢复、不同用户登录隔离、待办提示去重正常；未解决冲突时无高频空轮询。

后端扩展现有 `CollectionControllerTest`、`UserBgmCollectionSyncRunnerTest`，新增收藏服务、合并矩阵、冲突决议及数据库集成测试。数据库/锁/恢复语义使用真实 MySQL、Redis 测试环境验证，不能只靠 Mockito。

客户端扩展现有收藏 Provider/State/Tab 测试，增加同步 Provider、冲突页 Widget、空 ID 解析与缓存刷新测试。执行服务端相关模块 Maven 测试、Flutter analyze 与相关 Flutter 测试；真实 Bangumi 联调用专用测试账号，不对生产收藏做自动改写测试。

## 10. 上线与回退

1. 备份相关表，记录迁移前聚合基线，先部署加字段/建表等兼容迁移。
2. 用独立开关控制未绑定收藏和新版双向同步；先让服务端具备兼容返回，再发布支持新状态/空 ID 的客户端，最后开启新能力。
3. 旧客户端若不能消费空 ID 或冲突状态，采用 API 版本/能力协商或最低版本策略；不得通过伪造 Bangumi ID 掩盖兼容问题。
4. 灰度观察待同步积压、冲突数量、重试次数、授权错误、上游限流和成功耗时；日志不记录 token 或完整私密评论。
5. 回退优先关闭远端执行与新任务入口，保留本地收藏和已持久化决议。已有仅本地收藏后，不能直接恢复旧 `NOT NULL` 约束或旧清理逻辑。
6. MySQL 回滚不能撤销已经写入 Bangumi 的结果；需要依据操作快照人工核对，不能声称数据库回滚实现两侧整体回退。

完成标准：未绑定可以正常收藏；绑定后修改会上传且失败可见可恢复；同步保留双方收藏；分类冲突只有用户明确选择后才收敛；重试、换绑和并发不静默丢失本地修改。
