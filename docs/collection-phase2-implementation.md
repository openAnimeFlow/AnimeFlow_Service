# 收藏重构 P2/P3 阶段实现说明

本阶段开始落地持久化双向同步任务和人工冲突处理链路，服务端事实来源从 Redis 状态扩展为 MySQL 任务与明细表。

旧客户端兼容性及 Git 历史证据见 [收藏接口兼容性审查](collection-client-compatibility-review.md)。P1 客户端支持空 ID 不代表已支持 P2/P3 任务状态，发布前需单独验收。

## 已实现

- 新增 `user_bgm_collection_sync_task` 和 `user_bgm_collection_sync_item` 迁移脚本。
- 同步提交支持客户端 `requestId`，任务状态包含 `QUEUED`、`RUNNING`、`WAITING_CONFLICT`、`PARTIAL_FAILED` 等阶段。
- Bangumi 扫描发现本地版本与远端分类不一致时，保存冲突快照，不覆盖本地分类。
- 新增冲突查询接口：`GET /api/v1/users/collections/sync/{taskId}/conflicts`。
- 新增冲突决议接口：`POST /api/v1/users/collections/sync/{taskId}/conflicts/resolve`，校验用户归属、冲突版本和收藏类型。
- 账号设置页增加冲突条目选择界面，支持选择五种最终收藏类型；关闭页面后冲突仍由服务端任务保留。
- 客户端同步状态支持任务 ID、冲突数量和扩展任务状态。

## 本次 P1 审查修复

- 执行器只保留一个依赖注入构造函数，并增加 Spring 容器创建测试。
- 创建任务通过每用户命名锁串行处理，数据库生成列唯一键保证每用户最多一个活动任务；相同 requestId 在任务完成后仍返回原任务。
- 全量扫描五分类完成后才处理明细，按条目去重并纳入本地独有收藏。随后复用分页 interest 快照进行导入、未变化判断与初次冲突检测；仅可能写入远端的条目、用户冲突决议和异常恢复才按需读取详情，并在写入后核验。不会传播删除。
- 历史 version=0 收藏也比较分类；冲突明细阻止普通上传与自动重试。等待冲突时，其他条目的普通修改仍可上传。
- 决议校验用户归属、绑定记录与账号 UID、冲突版本、本地版本和远端快照。旧快照更新后返回 STALE_CONFLICT，要求重新选择。
- 用户选择先持久化为 RESOLUTION_PENDING，后台保存 APPLY_PENDING 写入意图及基线后才发起 HTTP。仅修改分类意图，保留评论、评分、标签、隐私等待上传字段。
- 远端确认后，在同一数据库事务内更新本地收藏、清理已发送脏字段并将明细标记 DONE。写后核验或本地版本不符时重新生成冲突，不静默覆盖。
- 接收和执行共用每用户任务锁、每条目收藏锁；重复提交相同冲突版本和相同分类返回原决议。远端已经达到目标值时不重复 PUT。
- 定时扫描器默认启动 60 秒后、每轮结束 60 秒后从数据库重新领取任务，恢复入库未启动、执行中断及失败明细；不依赖 Redis TTL 和客户端存活。配置项为 anime-flow.collection-sync.initial-delay-ms / retry-delay-ms。
- 批量决议在整批保存并释放锁后立即触发一次异步执行，避免每提交一条就启动执行器与同批下一条争锁；后续条目校验失败时仍触发前面已保存的决议。异步队列拒绝或进程中断时，由定时扫描器恢复。WAITING_CONFLICT 不持有长期锁；任务与明细仍持久保存。
- 执行器先跳过 DONE/CONFLICT 明细，再校验待执行条目的绑定，避免解决单个冲突时为全部已完成收藏重复查询 OAuth。2026-09-19 实测日志中旧逻辑保存决议到执行之间等待约 33 秒，实际执行约 0.4 秒，主要延迟来自等待定时扫描。
- 完成状态和导入、上传、冲突、失败、已解决数量从明细汇总，GET /sync 优先查活动任务，否则查询最近数据库任务。

## 部署及范围

- P1 数据库迁移后，依次执行 20260919_collection_sync_tasks.sql、20260920_collection_sync_recovery.sql，再部署代码；后者可升级已存在的任务表。
- 若已有重复活动任务，唯一键迁移会拒绝执行，需先核对处理重复任务，不自动删除记录。
- 初次实现验证仅在随机命名临时 MySQL 库演练。2026-09-19 真实场景排查时，已通过 mysql-mcp 在 anime_flow 补执行 20260920_collection_sync_recovery.sql：此前缺少 desired_payload、operation 和活动任务唯一约束，导致任务停在 SCANNING / PARTIAL_FAILED，尚未生成冲突。补齐后原任务由后台自动恢复到 APPLYING，无需删除或重建任务；后台会继续执行用户此前提交的同步。
- 客户端在 PARTIAL_FAILED 和 WAITING_CONFLICT 状态下每 10 秒继续查询，运行中每 2 秒查询，终态停止；避免服务端恢复或其他设备处理冲突后页面仍停留在旧状态。暂时失败显示可读重试提示。
- Bangumi 不提供条件写入，读取后与写入前的外部修改窗口仍存在；通过写后核验及可恢复快照处理，不能提供跨系统强事务。
- 本次修复覆盖服务端 P1 审查问题；客户端应用级待办提示、完整分页/国际化及旧客户端能力协商仍需单独验收。

## 分页收藏快照优化

- 新增 20260921_collection_sync_scan_snapshot.sql，已通过 mysql-mcp 在 anime_flow 添加 scan_snapshot；升级代码前须执行此迁移，旧任务字段为 NULL 时保留原读取流程。
- 快照保存完整 interest（包含收藏 ID、分类、评价、标签、隐私、进度与更新时间），普通导入与未变化条目不再逐条请求详情。分页快照不是跨系统实时视图；用户扫描后在 Bangumi 的修改可能在下次同步时体现。
- interest 为空且本地无收藏时不导入虚构收藏；本地有收藏且需要上传时按需查询远端。新扫描不再因为空 interest 直接失败。
- 可能写入远端时重新读取并比较基线；已准备写入的恢复任务忽略扫描快照，使用实时结果确认，避免重复 PUT 或覆盖扫描后的修改。
